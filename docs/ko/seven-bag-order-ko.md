# 7-bag 순서 제약 하의 퍼펙트 클리어 (w=10, n=10)

## 설정

    폭 10, 10 조각, R = 4 줄.
    조각은 bag1 (7 종 순열) -> bag2 (7 종 순열) 순으로 도착.
    홀드 1 칸, 표준 규칙.
    하드드롭 전용 (턱/스핀 없음)  => 결과는 보수적:
      "가능" 은 실제 테트리스에서도 반드시 가능
      "불가능" 은 우리 모델 한정 (스핀을 쓰면 뚫릴 수 있음)

10 회 배치에 소비하는 도착 조각은 최대 11 개 (홀드에 하나 남길 수 있으므로).
따라서 bag2 는 앞 4 개만 관여한다 -> bag2 접두사 P(7,4) = 840 가지.

    837 가능 / 4 불가능  (실패율 0.48%)

    bag2    결과        완전 탐색 상태 수
    OJZS    PC 없음     36,891,439
    OLZS    PC 없음     36,824,530

    LSOZ    가능        30,349,604
    나머지 834  가능 (상한 8M 안에서 즉시)

**구조.** 선별에서 걸린 6 개 후보가 전부 {O, S, Z} + {J 또는 L} 이었다.
그중 실패한 넷은 모두 **ZS 로 끝난다**. 가능한 둘은 OZ 로 끝난다.

    OJZS  OLZS  LOZS  JOZS   <- 실패 (전부 ...ZS)
    SLOZ  LSOZ              <- 가능 (...OZ)

bag1 = T J L I S Z O 자체가 S, Z, O 로 끝난다. S/Z 가 뒤에 몰리면 계단이 쌓이고
4 줄 안에서 풀 수단이 소진되는 구조로 보인다. Burgiel 정리가 가리키는 방향과 같다.

우리 모델 (하드드롭 전용) 에서의 불가능이다. 스핀/턱을 허용하면 달라질 수 있으므로
"실제 테트리스에서 불가능" 이라고 주장하면 안 된다.

## 구현 신뢰도

세 구현을 교차 검증했다.

    fix2.cpp   unordered_set<__int128>            키 = (보드, i, 홀드, mask2)
    fix4.cpp   개방 주소법 + 64 비트 지문, 2^27   키 = (보드, i, 홀드)
    fix5.cpp   개방 주소법 + 완전한 128 비트 키, 2^26

소규모 케이스에서 상태 수까지 정확히 일치. 대규모에서 fix2 가 약 2.6% 많은
상태를 세는데, 원인은 fix2 의 mask2 갱신이 경로마다 다르기 때문 (배치 분기는
갱신, 스태시 분기는 미갱신). mask2 는 bag2 순서 고정 이후 로직에 쓰이지 않고
메모 키에만 들어가므로, 같은 실제 상태가 중복 등록될 뿐 답은 같다.
fix4 와 fix5 는 정확히 일치하므로 지문 해싱 자체는 무해하다.

지문 계산에 잠재 버그가 하나 있었다: b (보드 상위 16 비트) 와 (i<<8)|hold 를
XOR 하면 비트가 겹쳐 조직적 충돌이 생긴다. b | (k << 16) 으로 분리해 수정했다.
이번 케이스들에서는 실제 충돌이 없었으나 (수정 전후 상태 수 동일) 구조적 결함이었다.

fix5 가 LOZS 에서 46,976,203 상태로 INCONCLUSIVE 를 냈는데
이는 2^26 * 0.7 = 46,976,204 와 일치하는 테이블 적재율 한계였다.
테이블이 두 배인 fix4 로 재실행해 완결했다. 숫자 일치 확인이 중요하다.

## 읽는 법

세 변수가 차례로 거의 닫혔다. 조각 구성은 전혀 장애물이 아니고, bag1 순서도
(bag2 가 자유라면) 장애물이 아니다. 양쪽을 다 고정했을 때 비로소 드물게 실패가 나온다.
표본 기준 실패율은 1/240 미만이며, 하드드롭 제한이 걸린 값이므로 실제로는 더 낮다.

=> **PCO, Jaws, 3 피스 오프너 같은 여러 셋업이 존재하는 이유는 "PC 가 없어서" 가 아니다.**
   PC 는 거의 항상 존재한다. 오프너는 존재성 문제의 답이 아니라
   **탐색 비용과 암기 비용** 문제의 답이다. 특정 셋업을 고정해 쓰기 때문에
   실전 성공률이 100% 에 못 미치는 것이지, 해가 없어서가 아니다.

## 계산 메모

상태 키를 (보드, 도착 인덱스 i, 홀드, bag2 마스크) 로 압축했다.
  - placed = i - [홀드 점유]              이므로 중복
  - clears 는 보드 칸 수 = 4*placed - 10*clears 로 결정되므로 중복
전부 합쳐 94 비트라 __int128 하나에 정확히 들어간다.

수 순서 휴리스틱 (구멍 수 우선, 그 다음 높이) 로 약 8 배 빨라졌다.
  어려운 케이스: 25,369,053 상태 118 초  ->  3,257,416 상태 15 초
fix.cpp (순서 없음) 와 fix2.cpp (순서 있음) 를 16 케이스에서 교차 검증, 전부 일치.

## 도구

    ./fix2 <도착 수열> [상태 상한]     예) ./fix2 IOTSZJLOJSZ 40000000
    ./survey.sh <bag1> <접두사 목록> <출력>
    ./runb2.sh  <bag1> <접두사 목록> <출력>   (fix 용, 상한 3M 고정)
    b2all.out : bag1=IOTSZJL 의 840 전수 결과

주의:
  - 백그라운드 프로세스는 툴 호출 사이에 죽는다. 120~140 개씩 청크로 돌리고 누적할 것.
  - 셸 루프에서 timeout 의 빈 출력을 반드시 검출할 것 (빈 출력 != 불가능).
  - 보드 비트폭: hcap * w = 80 비트이므로 u64 로는 잘린다. __int128 필수.

## 열린 문제

1. 5040 x 840 전수. 현재 속도로 약 수십 시간. 휴리스틱을 더 개선하거나 가지치기 필요.
2. 다른 bag1 에서도 "ZS 로 끝나는 {O,S,Z,J/L}" 패턴이 실패를 만드는지.
   TJLISZO 는 4/840 실패, IOTSZJL 은 0/840. 두 bag1 의 차이가 무엇인지.
3. 스핀/턱을 허용한 모델에서 그 실패가 살아남는지.
4. 실패율의 정확한 값. 표본 기준 < 1/240.
